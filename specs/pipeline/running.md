# Running

> This section is a draft. Its fields and rules can change before the section becomes `stable`.

A run starts a pipeline with run parameters. The same file runs in each running mode. This section gives the run parameters, the frame time, the running modes, the batch, the stateful pipelines, the session sharing, the warnings, the start checks, the param changes during a run, the CPU threads and the preprocess place ([ADR-N5BM](../../decisions/entries/N5BM-set-during-run-and-set-params.md); [ADR-ZYS9](../../decisions/entries/ZYS9-pipeline-outputs-running-sharing-inside-one-run.md) items 2 to 7; [ADR-V7GZ](../../decisions/entries/V7GZ-pipeline-api-device-and-vram-reserve.md) items 1, 6 and 7; [ADR-9NW0](../../decisions/entries/9NW0-ep-keys-options-and-failures.md) items 2, 4 and 5; [ADR-HB8Z](../../decisions/entries/HB8Z-cpu-threads-run-parameter.md); [ADR-W4NW](../../decisions/entries/W4NW-gpu-preprocess-of-a-model-node-and-its-cpu-warning.md); [ADR-0Q19](../../decisions/entries/0Q19-stored-jpeg-quick-check-stops-the-gpu-frame-path.md)).

## Fields

A pipeline file has no field of this section. A run takes these parameters:

| Parameter | Required | Description |
|-----------|----------|-------------|
| camera ids | yes | The ids of the cameras of the run. |
| running mode | yes | `image`, `video` or `live`. |
| execution provider | only when an `onnx_model` node has no `execution_provider` ([Behaviour](#behaviour) item 7) | A key of the EP catalog, for example `cuda`, `trt-rtx` or `cpu`. |
| EP options | no | A mapping of option names to values, all strings. The EP catalog lists the allowed names and values of each EP. Default: empty. |
| device | no | One GPU key or a list of GPU keys. The run uses exactly those GPUs. Default: each GPU that qualifies ([ADR-P1F3](../../decisions/entries/P1F3-hardware-probe-devices-and-multi-gpu.md)). |
| VRAM reserve | no | The bytes of VRAM that the run leaves free on each GPU that it uses, for example for a camera app and a player. In this version, the run uses it only for the camera split. Default: 1 GiB ([Behaviour](#behaviour) items 3 and 4; [ADR-V7GZ](../../decisions/entries/V7GZ-pipeline-api-device-and-vram-reserve.md) item 1). |
| `fps` | no | A float. Default: 30.0. Only in `video`, for a camera that gives no `timestamp_ms` ([Behaviour](#behaviour) item 2). |
| CPU threads | no | A positive integer: the intra-op thread count of each inference session of the run on the CPU EP `cpu` (`V-pipeline.running-11`). Default: half of the physical cores of the host, at least 1 ([Behaviour](#behaviour) item 7; [ADR-HB8Z](../../decisions/entries/HB8Z-cpu-threads-run-parameter.md)). The run also decodes the JPEG buffers of a call on the CPU with at most this count of threads at the same time ([Behaviour](#behaviour) item 13; [ADR-S1TG](decisions/entries/S1TG-cpu-jpeg-decode-threads.md)). |
| preprocess place | no | `auto`, `cpu` or `gpu`: the place of the preprocess of each `onnx_model` node. `auto` uses the GPU preprocess on `cuda` and `trt-rtx`, and the CPU preprocess on each other EP. `cpu` does the frame work on the CPU on each EP: the run decodes each JPEG buffer on the CPU, it uploads no frame, and each `onnx_model` node uses the CPU preprocess. Only the model runs on the EP. `cpu` is for a benchmark of the CPU path against the GPU path. `gpu` uses the GPU preprocess on each EP that has the wiring for it (`cuda`, `trt-rtx` and `directml`), also on an EP that no certification report confirms. `gpu` is for a certification run. Default: `auto` ([Behaviour](#behaviour) item 14; [ADR-W4NW](../../decisions/entries/W4NW-gpu-preprocess-of-a-model-node-and-its-cpu-warning.md) item 6). |
| timing | no | On or off, and the destination of the events ([Timing](timing.md)). |
| tap folder | no | The folder of the taps ([Taps](taps.md)). |
| user root | no | The user root of the model and pipeline files ([Pipeline file](file.md#behaviour)). |
| warning receiver | no | A receiver that gets each new warning. |

Each call gives, for each camera of the call, one frame with its `frame_index`. In `live`, each frame also has its `timestamp_ms` (a float, in milliseconds). In `video`, the frames of a camera have a `timestamp_ms` when the camera gives one ([Behaviour](#behaviour) item 2). A frame can have a `rotation_deg`: the degrees clockwise that the stored image must turn to be upright, `0`, `90`, `180` or `270`. Default: `0` ([Behaviour](#behaviour) item 13; `V-pipeline.running-13`).

The image of a frame has one of these two forms. Each frame of a call can have either form ([ADR-75K2](../../decisions/entries/75K2-unclear-places-of-the-pipeline-spec.md); [ADR-P245](decisions/entries/P245-jpeg-frame-input.md)):

- a decoded array: the host frame, BGR, `uint8`, shape `(H, W, 3)`, in CPU memory;
- a JPEG buffer: the bytes of one JPEG image. The run decodes it to `frame.image` before the first node ([Behaviour](#behaviour) item 13).

A warning has these fields ([ADR-V7GZ](../../decisions/entries/V7GZ-pipeline-api-device-and-vram-reserve.md) item 6):

| Field | Description |
|-------|-------------|
| `code` | `batch_limited_by_state`, `ep_partial_placement`, `jpeg_decoded_on_cpu`, `merge_part_without_landmark_schema`, `merge_unfilled_points`, `missing_dependency`, `output_group_without_landmark_schema` or `preprocessed_on_cpu`. |
| `message` | A text for people. The log line uses the same text. |
| `node_ids` | The ids of the nodes that the warning is about. |
| `details` | A mapping with more facts. |

## Behaviour

1. **Running modes.** The run sets the running mode. The file is the same in each mode ([ADR-ZYS9](../../decisions/entries/ZYS9-pipeline-outputs-running-sharing-inside-one-run.md) item 2):
   - `image`: each `@prev` value is empty. The frame size can change from call to call. The run has one camera.
   - `video`: the run gets each frame in order.
   - `live`: `frame_index` can skip. The caller drops frames. The run drops no frame.
2. **Frame time.** The temporal nodes use `timestamp_ms` ([ADR-ZYS9](../../decisions/entries/ZYS9-pipeline-outputs-running-sharing-inside-one-run.md) item 2):
   - `live`: each frame must have a `timestamp_ms` (`V-pipeline.running-6`). There is no fallback.
   - `video`: each camera gives `timestamp_ms` on all its frames or on none (`V-pipeline.running-7`). For a camera that gives none, the run uses `timestamp_ms = frame_index × 1000 / fps` ([ADR-97X9](../../decisions/entries/97X9-pipeline-instance-rows-prev-types-and-refused-calls.md) item 8).
   - `image`: the run uses no `timestamp_ms`.
   - The `timestamp_ms` of a camera must increase from frame to frame ([`V-node.smooth_keypoints-3`](nodes/smooth_keypoints.md#validation-rules)).
   - A call that breaks `V-pipeline.running-6`, `V-pipeline.running-7` or [`V-node.smooth_keypoints-3`](nodes/smooth_keypoints.md#validation-rules) raises the typed error `CallRefusedError`. The call changes no state of any of its cameras, also no `@prev` value. The run accepts the next call ([ADR-97X9](../../decisions/entries/97X9-pipeline-instance-rows-prev-types-and-refused-calls.md) item 9; [ADR-0YNA](../../decisions/entries/0YNA-public-names-standard-and-four-renames.md)).
3. **Cameras.** In `video` and `image`, each call gives one frame for each camera id of the run. In `live`, a call can hold a subset of the camera ids of the run ([ADR-ZYS9](../../decisions/entries/ZYS9-pipeline-outputs-running-sharing-inside-one-run.md) item 3). A run with two or more GPUs splits its cameras over the GPUs. Each GPU runs the whole pipeline for its cameras ([ADR-P1F3](../../decisions/entries/P1F3-hardware-probe-devices-and-multi-gpu.md) item 7). The split is fixed at start ([ADR-AMF7](../../decisions/entries/AMF7-camera-split-by-vram.md)):
   - The GPUs are in the order of the GPUs of the run: the GPU with the most VRAM first. On a tie, the GPU with the lowest PCI bus id is first.
   - The weight of a GPU is the VRAM that the run can use on it: the free VRAM at start minus the VRAM reserve, with a floor of 0. When the host cannot read the free VRAM of each GPU of the run, the weight is the total VRAM minus the VRAM reserve, with a floor of 0. When the host cannot read the total VRAM of each GPU of the run, or each weight is 0, all weights are equal.
   - With `n` cameras and the weights `w_i`, the quota of GPU `i` is `w_i × n / Σw`. Each GPU gets the integer part of its quota. The cameras that remain go one each to the GPUs with the largest fractional parts. On a tie, the earlier GPU gets the camera. The run uses exact arithmetic for the quotas. Thus GPUs with equal weights get equal counts, and the extra cameras go to the first GPUs.
   - Each GPU that the run uses gets one camera or more. Each GPU with the count 0, in GPU order, takes one camera from the GPU with the largest count. On a tie, it takes the camera from the earlier GPU.
   - A run with fewer cameras than GPUs uses only the first GPUs, with one camera each.
   - The run gives the cameras to the GPUs in the order of the camera ids: the first cameras to the first GPU, the next cameras to the second GPU, and so on.
4. **Batch.** The run chooses the batch at start ([ADR-ZYS9](../../decisions/entries/ZYS9-pipeline-outputs-running-sharing-inside-one-run.md) item 4):
   - The batch on a GPU is k × the camera count of that GPU. In this version, k is 1 on each GPU. The run uses the VRAM reserve only for the camera split (Behaviour item 3) ([ADR-V7GZ](../../decisions/entries/V7GZ-pipeline-api-device-and-vram-reserve.md) item 1; [ADR-75K2](../../decisions/entries/75K2-unclear-places-of-the-pipeline-spec.md) item 1).
   - In `live`, the batch is the camera count.
   - In `video`, the batch of a stateful pipeline is the camera count (Behaviour item 5).
   - A node that takes boxes batches to that batch × the `I` of the instance source of its box input. The run converts the batch at start.
   - The run converts each artifact with `batching.batch: 3` to its batch at start ([Batch conversion](../model-sidecar/common/batch-conversion.md)).
   - The run pads a missed frame. It gives a blank crop to each empty crop slot, for example the slot of a padding box row. It drops the result of each padded item.
5. **Stateful pipelines.** A pipeline is stateful when it has an `@prev` input, or a temporal node upstream of an `onnx_model` node. The temporal nodes are `smooth_boxes`, `smooth_keypoints`, `redetect_trigger`, and `mediapipe_tasks` in the landmarker mode `VIDEO`. A temporal node with no `onnx_model` node downstream does not make a pipeline stateful. `hold_boxes` keeps no state, so it is not a temporal node. Each temporal node keeps a separate state for each camera. The node section gives the state of one camera. In `live`, a camera that a call does not hold keeps its state ([ADR-97X9](../../decisions/entries/97X9-pipeline-instance-rows-prev-types-and-refused-calls.md) item 7). In `video`, a stateful pipeline runs at batch = camera count. There is no switch to turn this off. The run writes one log line that names the stateful nodes, and gives the warning `batch_limited_by_state` ([ADR-ZYS9](../../decisions/entries/ZYS9-pipeline-outputs-running-sharing-inside-one-run.md) item 5).
6. **Session sharing only inside one run.** A run owns its inference sessions. In one run, the nodes with the same artifact SHA-256, batch, EP key, EP options and device share one inference session. The file does not control this. No session is shared between runs: two runs are two sets of sessions. `close()` frees the sessions of the run ([ADR-ZYS9](../../decisions/entries/ZYS9-pipeline-outputs-running-sharing-inside-one-run.md) item 6).
7. **Execution provider.** The EP key and the EP options are parameters of the run. The EP catalog in `core/eps/` owns the EP keys and lists the allowed options of each EP ([ADR-9NW0](../../decisions/entries/9NW0-ep-keys-options-and-failures.md) items 1 and 2). An `onnx_model` node can give its own EP in `execution_provider` and its own options in `ep_options`. The EP of the run applies to each `onnx_model` node that has no `execution_provider`. A run must give an EP when such a node exists (`V-pipeline.running-8`). A run of a pipeline with no `onnx_model` node must not give an EP (`V-pipeline.running-9`). A `mediapipe_tasks` node never uses an EP. One pipeline can hold `onnx_model` nodes and `mediapipe_tasks` nodes ([ADR-9PDQ](../../decisions/entries/9PDQ-pipeline-renames-and-the-run-ep.md) item 4). There is no EP policy such as `recommended:latency`. The caller resolves a recommended form to an EP key and its options ([ADR-7NY2](../../decisions/entries/7NY2-pipeline-form-graph-and-nodes.md) item 12; [ADR-9NW0](../../decisions/entries/9NW0-ep-keys-options-and-failures.md) item 3).
   - A run never uses another EP than the requested EP. An EP that is not available or does not start stops the start of the run before frame 0 ([ADR-9NW0](../../decisions/entries/9NW0-ep-keys-options-and-failures.md) item 4).
   - An out-of-memory error of a session during a call raises `VRAMExhaustionError`, the error of an out-of-memory error at start. The run does not do the call again, and it does not change the batch. The run is then closed: each later call raises an error ([ADR-2V7Q](../../decisions/entries/2V7Q-out-of-memory-during-a-call.md)).
   - A session can have nodes on the CPU EP. The run reports them ([ADR-9NW0](../../decisions/entries/9NW0-ep-keys-options-and-failures.md) item 5).
   - **CPU threads.** Each session on the CPU EP `cpu` uses the CPU threads of the run as its intra-op thread count, and one inter-op thread. When the run gives no CPU threads, the count is half of the physical cores of the host, at least 1. When the host gives no physical core count, the count is half of the logical CPUs, at least 1. Thus the run leaves cores free for the camera capture and the application. A session of a GPU EP pack uses one intra-op thread and one inter-op thread, and ignores the CPU threads. A session on another built-in EP, for example `coreml`, uses the thread counts of ONNX Runtime. A `mediapipe_tasks` node is not an ONNX session: it does not use the CPU threads. The run decodes the JPEG buffers of a call on the CPU with at most the CPU threads at the same time (Behaviour item 13; [ADR-S1TG](decisions/entries/S1TG-cpu-jpeg-decode-threads.md)). The run reports the applied count in `cpu_threads` of the `execution` facts ([Timing](timing.md#fields)) ([ADR-HB8Z](../../decisions/entries/HB8Z-cpu-threads-run-parameter.md)).
8. **Warnings.** The run gives a warning for each of these conditions ([ADR-V7GZ](../../decisions/entries/V7GZ-pipeline-api-device-and-vram-reserve.md) items 6 and 7):
   - `batch_limited_by_state`: the pipeline is stateful and the running mode is `video` (Behaviour item 5).
   - `ep_partial_placement`: a session of the node has nodes on the CPU EP. `details` gives the node count of each EP and the CPU op types. The run gives it one time for each session ([ADR-9NW0](../../decisions/entries/9NW0-ep-keys-options-and-failures.md) item 5).
   - `jpeg_decoded_on_cpu`: the run decodes JPEG buffers on the CPU in place of the GPU decoder (Behaviour item 13). The run gives it one time for each camera with a JPEG buffer that the GPU decoder refuses, and `details` gives the camera id. The run also gives it one time for the run, at the first call with a JPEG buffer on a device with a node that uses the GPU preprocess, when the GPU decoder of that device does not open, for example because its package is not installed. `details` then gives the name of that package. The run also gives it one time for the run, at the first call with a JPEG buffer on a device where a stored quick check moves the decode to the CPU, with the reason `quick_check_failed` (Behaviour item 13; [ADR-0Q19](../../decisions/entries/0Q19-stored-jpeg-quick-check-stops-the-gpu-frame-path.md)). A call that the run refuses before the first node gives no such warning. A run that gets only decoded arrays gets no such warning. Except for the reason `quick_check_failed`, a JPEG buffer of a device with no node that uses the GPU preprocess gives no such warning. A run with the preprocess place `cpu` gives no such warning (Behaviour item 14). `node_ids` is empty ([ADR-P245](decisions/entries/P245-jpeg-frame-input.md)).
   - `merge_part_without_landmark_schema`: a part of a `merge` node has a null `landmark_schema`, so the load cannot check its region (`V-node.merge-8`). A load gives this warning. `details` gives the part ([Node: merge](nodes/merge.md#validation-rules); [ADR-9HTX](../../decisions/entries/9HTX-pipeline-node-and-port-redesign.md) item 11).
   - `merge_unfilled_points`: a slot of an `assign_keypoints` node or a part of a `merge` node replaces a group, and one or more points of that group are unfilled and no key of `map` names them. A load gives this warning. `details` lists the points ([Node: assign keypoints](nodes/assign_keypoints.md#behaviour) item 5; [Node: merge](nodes/merge.md#behaviour) item 3; [ADR-KW76](../../decisions/entries/KW76-merge-replace-add-and-hungarian-match.md) item 2).
   - `missing_dependency`: a node needs an optional extra that is not installed, or an ONNX file that is absent or whose hash does not agree. A load gives this warning. A start fails before frame 0 ([Validation rules](#validation-rules)). For a node with no `precision`, a load gives the warning only when no artifact of the size is usable. A start checks the artifact of the EP (`V-pipeline.running-3`) ([ADR-75K2](../../decisions/entries/75K2-unclear-places-of-the-pipeline-spec.md) item 3).
   - `output_group_without_landmark_schema`: a group of the port of the output `wholebody` has a null `landmark_schema`, so it passes through the canonical form with its names. A load gives this warning, one time for each such group. `details` gives the output key, the port and the group ([Outputs](outputs.md#behaviour) item 6; [ADR-9HTX](../../decisions/entries/9HTX-pipeline-node-and-port-redesign.md) item 14). The output `holistic` gives no such warning: its MediaPipe groups have a null `landmark_schema`.
   - `preprocessed_on_cpu`: an `onnx_model` node that must use the GPU preprocess uses the CPU preprocess. With the preprocess place `auto`, a node on the EP `cuda` or `trt-rtx` must use the GPU preprocess. With `gpu`, a node on each EP must use it (Behaviour item 14). With the GPU preprocess, the node runs its preprocess as a graph in its own session, and binds the output of the graph to the model input in GPU memory. The node uses the CPU preprocess for each of these reasons: the graph refuses the combination of the node, for example `interpolation: area` ([Resize limit](../model-sidecar/pre/interpolation.md#resize-limit)); a graph session does not build; a call has a new set of frame sizes, and the node already has graph sessions for 4 sets of frame sizes on that device. The run gives the warning one time for each node and reason, at the first call that uses the CPU preprocess for that reason. `node_ids` holds the node. `details` gives the node, the reason and the frame sizes of that call. With `gpu`, a node on an EP that has no wiring for the GPU preprocess uses the CPU preprocess for the reason `ep_not_wired`. The run gives that warning one time for each node, at the start of the run, and the frame sizes of `details` are null. With `auto`, a node on a device where a stored quick check gives `fail` for `jpeg-preprocess` uses the CPU preprocess on that device for the reason `quick_check_failed` (Behaviour item 13; [ADR-0Q19](../../decisions/entries/0Q19-stored-jpeg-quick-check-stops-the-gpu-frame-path.md)). The run gives that warning one time for each node, at the start of the run, and the frame sizes of `details` are null. With `auto`, a node on another EP gives no such warning. With `cpu`, the run gives no such warning (Behaviour item 14) ([ADR-W4NW](../../decisions/entries/W4NW-gpu-preprocess-of-a-model-node-and-its-cpu-warning.md)).
   - The load result holds the warnings that are known before start, the output schema, and a flag that is true when a run must give an EP (`V-pipeline.running-8`) ([ADR-75K2](../../decisions/entries/75K2-unclear-places-of-the-pipeline-spec.md)). The run holds the full list. The run gives each new warning to the warning receiver one time, also during the run, from the thread that makes the call.
9. **Replayed and unused ports.** A port is used when it is an output, an input of a node that runs, or the port of a `record` tap. A node whose outputs are all replayed or not used does not run. The upstream nodes of a replayed port do not run when nothing else uses them ([Taps](taps.md#behaviour)).
10. **Start checks.** The run does these checks before frame 0 ([ADR-ZYS9](../../decisions/entries/ZYS9-pipeline-outputs-running-sharing-inside-one-run.md) item 7): `V-pipeline.running-3`, `V-pipeline.running-4`, `V-pipeline.running-5`, `V-pipeline.running-8`, `V-pipeline.running-9`, `V-pipeline.running-11`, [`V-pipeline.taps-2`](taps.md#validation-rules), [`V-pipeline.taps-3`](taps.md#validation-rules), [`V-pipeline.taps-4`](taps.md#validation-rules), [`V-pipeline.taps-5`](taps.md#validation-rules), [`V-pipeline.taps-6`](taps.md#validation-rules) and [`V-pipeline.taps-7`](taps.md#validation-rules).
11. **Params during a run.** `PipelineRun.set_params(node_id, params)` sets params of one node ([ADR-N5BM](../../decisions/entries/N5BM-set-during-run-and-set-params.md)):
    - Only a param that the node table marks `yes` in the column "Set during run" can change. The run checks each value against the type and the range of the param, as the load does.
    - The run accepts the call in each running mode before the first `process` or `process_batch` call. After that call, it accepts the call only in `live`, and only when the run has no `record` tap ([Taps](taps.md#behaviour)).
    - A change applies from the next `process` or `process_batch` call, to each camera. It does not reset the state of a node. A param whose change would need a reset is marked `no`.
    - A call that breaks `V-pipeline.running-10` raises the error `SetParamsRefusedError`. It changes no param.
12. **Threads.** The calls on one run are serial: a second call waits for the first call. `close()` waits for the call that runs. A call after `close()` raises an error. A second `close()` does nothing. Two runs share no state. There is no cancel ([ADR-75K2](../../decisions/entries/75K2-unclear-places-of-the-pipeline-spec.md) item 5).
13. **JPEG frames.** The caller gives the image of each frame as a decoded array or as a JPEG buffer ([Fields](#fields)). The pipeline file is the same for both forms ([ADR-P245](decisions/entries/P245-jpeg-frame-input.md)):
    - The run decodes each JPEG buffer, then turns the decoded frame clockwise by the `rotation_deg` of the frame. Both steps occur before the first node of the call. `frame.image` is the turned frame for each reader. Each node reads `frame.image` as for a decoded array.
    - The run decodes and turns each JPEG buffer one time. Each reader of `frame.image` gets the same frame.
    - The run does not apply the EXIF orientation of a JPEG.
    - The turned frame is an 8-bit image with 3 channels in BGR order. For `rotation_deg` `0` and `180`, its width and height are the stored width and height of the JPEG. For `90` and `270`, its width and height are the stored height and width.
    - The turn is exact. It moves the pixel values and changes none.
    - A decoded array can have a `rotation_deg`. The run turns the array clockwise by it before the first node. For `90` and `270`, its width and height swap. The run does not change the array of the caller. With `rotation_deg` `0`, the run can use the array as it is.
    - A call with a `rotation_deg` that is not `0`, `90`, `180` or `270` breaks `V-pipeline.running-13`. It raises `CallRefusedError`, with the same effect as in Behaviour item 2.
    - The run decodes on the GPU the JPEG buffers of the cameras of a device with an `onnx_model` node that uses the GPU preprocess on the EP `cuda` or `trt-rtx` (Behaviour item 8, `preprocessed_on_cpu`). The run decodes each other JPEG buffer on the CPU, with no warning. A stored quick check can move the decode of such a device to the CPU, with a warning (the item "Stored quick check" below).
    - On the EP `directml`, a node can use the GPU preprocess with `gpu` (Behaviour item 14). The run then decodes each JPEG buffer on the CPU, with no warning.
    - When a node on the device of a camera uses the GPU preprocess, the decoded frame of that camera can be in GPU memory. Else the decoded frame is in CPU memory.
    - The spec does not give the pixel values of the decode. Two decoders can give different pixel values for one JPEG. The spec requires only the width, the height, the channel count, the channel order and the bit depth.
    - When the GPU decoder refuses a JPEG buffer, for example a JPEG with no Huffman tables (no DHT segment), the run decodes that frame on the CPU. The call continues. The run gives the warning `jpeg_decoded_on_cpu` (Behaviour item 8).
    - When an `onnx_model` node that runs uses the GPU preprocess on the EP `cuda` or `trt-rtx` and the GPU decoder does not open, for example because its package is not installed, the run decodes each JPEG buffer of that device on the CPU. The start does not fail. The run gives the warning `jpeg_decoded_on_cpu` at the first call with a JPEG buffer (Behaviour item 8).
    - **Stored quick check.** The quick check of `skellytracker.certify()` stores the result of the JPEG checks `jpeg-decode` and `jpeg-preprocess` for an EP on a GPU of the PC ([ADR-R53H](../../decisions/entries/R53H-quick-check-default-eps-and-each-gpu.md) item 5). With the preprocess place `auto`, the run reads this stored result at the start, for the EP and the GPU of each device with an `onnx_model` node on the EP `cuda` or `trt-rtx` ([ADR-0Q19](../../decisions/entries/0Q19-stored-jpeg-quick-check-stops-the-gpu-frame-path.md)):
      - Only a stored `fail` changes the run. A stored `pass` or `not-run`, no stored result for the EP and the GPU, and a stored result that the run cannot read keep the GPU frame path. The read never stops the start.
      - Each check stops only its own part of the GPU frame path, on that device only. The model sessions stay on the EP.
      - `jpeg-decode` is `fail`: no GPU decoder opens on that device. The run decodes each JPEG buffer of that device on the CPU. The GPU preprocess still runs: the frame stage uploads the decoded frames, as for a decoder that does not open. The run gives the warning `jpeg_decoded_on_cpu` with the reason `quick_check_failed` (Behaviour item 8).
      - `jpeg-preprocess` is `fail`: each `onnx_model` node on that EP uses the CPU preprocess on that device from the start of the run. The run gives the warning `preprocessed_on_cpu` with the reason `quick_check_failed` (Behaviour item 8). A frame in GPU memory has no use without the GPU preprocess, so the run also decodes each JPEG buffer of that device on the CPU, and no frame of that device uploads. The decode thus moves to the CPU, so the run also gives the warning `jpeg_decoded_on_cpu` with the reason `quick_check_failed`. `stage_providers.preprocess` of the node is null when that device is the first GPU of the node ([Timing](timing.md#fields)).
      - With the preprocess place `gpu`, the run does not read the stored result, and it uses the GPU frame path. Thus a certification run or a developer can run that path again. With `cpu`, the run does not read the stored result (Behaviour item 14).
    - A call with a JPEG buffer that no decoder can read breaks `V-pipeline.running-12`. It raises `CallRefusedError`, with the same effect as in Behaviour item 2: the call changes no state of any of its cameras, and the run accepts the next call.
14. **Preprocess place.** The run parameter preprocess place sets where each `onnx_model` node does its preprocess. Its value is `auto`, `cpu` or `gpu`. A run with another value fails at the start, before frame 0 ([ADR-W4NW](../../decisions/entries/W4NW-gpu-preprocess-of-a-model-node-and-its-cpu-warning.md) item 6):
    - `auto`, the default: a node on the EP `cuda` or `trt-rtx` uses the GPU preprocess. A node on each other EP uses the CPU preprocess. A certification report confirms the GPU preprocess on these two EPs. The run is as Behaviour items 8 and 13 give. `directml` has the wiring, but `auto` does not use it: no certification report from AMD hardware confirms it yet.
    - `gpu`: a node on each EP that has the wiring for the GPU preprocess uses the GPU preprocess, also when no certification report confirms that EP. `gpu` is for a certification run. In this version, `cuda`, `trt-rtx` and `directml` have the wiring. On `cuda` and `trt-rtx`, `gpu` is thus the same as `auto`. On `directml`, `gpu` uses the GPU preprocess, and `auto` uses the CPU preprocess with no warning. A node on an EP with no wiring, for example `cpu` or `coreml`, uses the CPU preprocess. The run then gives the warning `preprocessed_on_cpu` with the reason `ep_not_wired` (Behaviour item 8). `gpu` does not read the stored quick check: a stored `fail` does not change the run (Behaviour item 13).
    - `cpu`: the run does the frame work on the CPU on each EP:
      - Each `onnx_model` node uses the CPU preprocess. The run builds no preprocess graph session.
      - No node uses the GPU preprocess, so the run decodes each JPEG buffer on the CPU, with at most the CPU threads at the same time (Behaviour item 13). No GPU decoder opens.
      - The run uploads no frame to GPU memory. Each decoded frame is in CPU memory.
      - Only the inference session of each `onnx_model` node runs on the EP of the node.
      - The run gives no warning `preprocessed_on_cpu` and no warning `jpeg_decoded_on_cpu` (Behaviour item 8).
      - `stage_providers.preprocess` of each node item is null from the start of the run, because the preprocess runs on the host ([Timing](timing.md#fields)).

## Validation rules

- [ ] `V-pipeline.running-1` The camera ids must be a non-empty list of unique ids. In the running mode `image`, the list must hold exactly one id.
- [ ] `V-pipeline.running-2` In `video` and `image`, each call must give a frame for each camera id of the run, and no frame for another id. In `live`, each call must give a frame for one or more camera ids of the run, and no frame for another id.
- [ ] `V-pipeline.running-3` Each ONNX artifact of each node that runs must be present, with the SHA-256 that its sidecar gives. Each optional extra that a node that runs needs must be installed. Else the start must fail before frame 0 with an error that names the extra or the file, and the nodes.
- [ ] `V-pipeline.running-4` The EP of each `onnx_model` node that runs must be a key of the EP catalog that is not reserved and is ready on the host. Its EP options must be names and values that the catalog allows for that EP ([ADR-9NW0](../../decisions/entries/9NW0-ep-keys-options-and-failures.md) items 1, 2 and 4).
- [ ] `V-pipeline.running-5` A node that runs must have no replayed output port.
- [ ] `V-pipeline.running-6` In the running mode `live`, each frame must have a `timestamp_ms`.
- [ ] `V-pipeline.running-7` In the running mode `video`, each camera must give a `timestamp_ms` on each of its frames or on none of its frames.
- [ ] `V-pipeline.running-8` When the pipeline has an `onnx_model` node with no `execution_provider`, the run must give an EP ([ADR-9PDQ](../../decisions/entries/9PDQ-pipeline-renames-and-the-run-ep.md) item 4).
- [ ] `V-pipeline.running-9` When the pipeline has no `onnx_model` node, the run must not give an EP ([ADR-9PDQ](../../decisions/entries/9PDQ-pipeline-renames-and-the-run-ep.md) item 4).
- [ ] `V-pipeline.running-10` A `set_params` call must name a node of the run. Each param must be a param of that node type, marked `yes` in the column "Set during run", with a value of its type and range. After the first `process` or `process_batch` call, the running mode must be `live` and the run must have no `record` tap ([ADR-N5BM](../../decisions/entries/N5BM-set-during-run-and-set-params.md)).
- [ ] `V-pipeline.running-11` When the run gives CPU threads, the value must be a positive integer. A boolean is not a valid value. Else the start must fail before frame 0 ([ADR-HB8Z](../../decisions/entries/HB8Z-cpu-threads-run-parameter.md)).
- [ ] `V-pipeline.running-12` Each JPEG buffer of a call must be a JPEG image that a decoder of the run can read. Else the call must raise `CallRefusedError` ([ADR-P245](decisions/entries/P245-jpeg-frame-input.md)).
- [ ] `V-pipeline.running-13` The `rotation_deg` of a frame must be `0`, `90`, `180` or `270`. Else the call must raise `CallRefusedError` ([ADR-P245](decisions/entries/P245-jpeg-frame-input.md)).

## Implementer guidance

- The runtime builds each ONNX session with `eps.build_session()`. The `execution` facts of the timing header come from that build ([ADR-V7GZ](../../decisions/entries/V7GZ-pipeline-api-device-and-vram-reserve.md) item 5).
- The availability of an extra comes from `importlib.util.find_spec` with a literal name, the presence of each ONNX file and its hash ([ADR-V7GZ](../../decisions/entries/V7GZ-pipeline-api-device-and-vram-reserve.md) item 7).
- The warnings do not use the Python `warnings` module ([ADR-V7GZ](../../decisions/entries/V7GZ-pipeline-api-device-and-vram-reserve.md) item 6).
- The run parameter "frame interval" of the first draft is removed. The temporal nodes use `timestamp_ms` in each mode that keeps state.
- JPEG frames ([ADR-P245](decisions/entries/P245-jpeg-frame-input.md)):
  - The package can give the decoded frame its own type, for example `DecodedFrame`. The type name is not a part of the spec.
  - The decoders are an implementation choice: `cv2.imdecode` on the CPU, and nvJPEG through nvImageCodec on `cuda` and `trt-rtx`.
  - nvImageCodec applies the EXIF orientation by default (`apply_exif_orientation` defaults to True), and `cv2.imdecode` applies it unless `cv2.IMREAD_IGNORE_ORIENTATION` is set, so the run turns both off.
  - The turn: `rotation_deg` `90` is `cv2.ROTATE_90_CLOCKWISE`, `180` is `cv2.ROTATE_180`, and `270` is `cv2.ROTATE_90_COUNTERCLOCKWISE`. On the CPU, the run uses `cv2.rotate`, also for a decoded array. On the GPU, the run uses a small graph of exact pixel moves. TensorRT takes a `uint8` tensor only as the input of a `Cast`, so the graph casts, moves and casts back, and the result is still exact. A turn inside each resize graph was measured and not chosen.
  - On the GPU, a turn after the decode costs 0.06 to 0.15 ms for each frame. A decode that applies an EXIF tag costs about 0.1 to 0.3 ms more for 90 and 270 degrees. On the CPU, the two costs are equal.
  - The decoder option `nvjpeg_cuda_decoder:hybrid_huffman_threshold=500000` moves the Huffman step to the GPU for frames with more than 500000 pixels. The library default is 1000000. On one RTX 3070, it cut `frame.decode` of 3 frames at 1280x720 from about 2.5 to 1.5 ms on `cuda`, and from 2.4 to 1.4 ms on `trt-rtx`, with identical pixels ([ADR-BP5Y](../../decisions/entries/BP5Y-gpu-huffman-decode-threshold.md)). The threshold 0 makes the decode of 320x240 frames slower. The package uses 500000. It is tested on one GPU only.
  - nvJPEG and `cv2.imdecode` differ by at most 3 `uint8` steps. The mean is 0.024 for one image at 1280x720 with 4:2:2 chroma and JPEG quality 90, and 0.018 on 150 frames of the freemocap sample data ([ADR-FBV5](../../decisions/entries/FBV5-gpu-path-agreement-on-the-freemocap-sample-data.md)). On 148 frame variants at quality 90 with 4:2:2 and 4:2:0 chroma, the `letterbox` model input from the two decoders differs by a mean of 0.0099.
  - nvImageCodec falls back to a CPU decoder by itself and gives no signal of it, so the run uses a decoder that is limited to the nvJPEG backends `GPU_ONLY` and `HYBRID_CPU_GPU` and does its own CPU fallback to give the warning `jpeg_decoded_on_cpu`. With these backends, the decoder refuses a JPEG with no Huffman tables (no DHT segment). On one RTX 3070 it decodes a progressive JPEG, a grayscale JPEG and a CMYK JPEG. `import nvidia.nvimgcodec` prints errors for nvJPEG2000 and nvTIFF. The JPEG decode is not affected.
  - nvImageCodec accepts `bytes`, `bytearray` and a 1-D `uint8` array, and refuses a `memoryview`.
  - `cv2.imdecode` raises an assertion error for an empty buffer, so the run checks for an empty buffer first: an empty buffer is not a JPEG image (`V-pipeline.running-12`).
  - The JPEG frames of a call share one decode batch, also when their stored sizes or their `rotation_deg` values are different.
  - On the CPU, the run decodes the JPEG buffers of a call in a thread pool when the call has 2 or more such buffers and `cpu_threads` is more than 1. A refused call names the first camera in camera order with a buffer that no decoder can read ([ADR-S1TG](decisions/entries/S1TG-cpu-jpeg-decode-threads.md)).
  - The lossless turn of the JPEG data is not a way to turn a frame: it cannot turn each size, because of a partial block at the edge, and it is slower than the decode and a turn.
  - The GPU decoder returns before the frame is complete. The run waits for the decode before a reader uses the frame.
  - With nvImageCodec 0.10.0.9, a decode of exactly one image never returns when the decoder has fewer CUDA streams than worker threads: the threads that share a stream wait at a barrier, and one image wakes only one thread. A batch of 2 or more images returns. nvImageCodec limits the thread count to the CPU count minus 1. It takes the option `num_cuda_streams` only from 1 to the thread count. Else it uses the environment variable `NVIMGCODEC_DEFAULT_NUM_CUDA_STREAMS` when that is from 1 to the thread count, and else the thread count. The run must set the thread count and the stream count to the same value, at most the CPU count minus 1, and must remove the environment variable before it makes the decoder. The package uses at most 8.
  - At the open, the run decodes one small JPEG in a separate thread and waits at most 10 s. When that decode raises, gives no image or does not return, the decoder does not open, as for a missing package. The run does not close a decoder whose decode did not return, because a thread waits in it.
  - The run closes in this order: the IO bindings, the decoded frames, the sessions, the decoder, the CUDA stream. The run does not rely on the end of the process to close them.
  - When the open of the GPU decoder raises an error, the run decodes on the CPU and gives the warning `jpeg_decoded_on_cpu`, as for a decoder that does not open. The run does not catch an error of a decode: the call raises it.
  - The `details` of `jpeg_decoded_on_cpu` have the key `reason`. For a buffer that the GPU decoder refuses, `reason` is `decoder_refused`, and `camera_id` gives the camera. For a decoder that does not open, `reason` is `decoder_unavailable`, `package` gives the package, `jpeg_decoder` gives its install state, `install_hint` gives the install command or null, and `cause` gives the error text of the open or null. For a stored quick check, `reason` is `quick_check_failed`, with no other key.
  - The stored quick check (Behaviour item 13; [ADR-0Q19](../../decisions/entries/0Q19-stored-jpeg-quick-check-stops-the-gpu-frame-path.md)): the stored result is the field `jpeg` of the row of the pair in the file `quick-checks.json` of the EP store. The pair is the EP key, the pack version, the OS and the PCI ids of the GPU (`pair_key` of `core/eps/certification.py`). The run finds the GPU of a device in the host record of its start check, and does not probe the host again. It reads the file one time for each node and device, at the start only, with no lock: the writer replaces the file in one step, and the lock would make the store folder. Thus the run writes nothing to the EP store. A new quick check of the pair that ends `pass` or `fail` replaces the row, also its `jpeg`. A new pack version gives a new pair with no stored result. Two GPUs of one model share one row.
  - The run uploads a frame from CPU memory to GPU memory at most one time for each call, in the frame stage, before the first node. The run uploads the frame of a camera when a node on the device of that camera uses the GPU preprocess ([Timing](timing.md#fields), the span `frame.upload`). On `directml`, the frame stage keeps the frame in CPU memory, and each preprocess session copies it to GPU memory in its own run (the next list).
  - A node that needs the pixels in CPU memory, for example `mediapipe_tasks`, copies a frame in GPU memory to the host as a part of the conversion for its model ([Graph](graph.md#behaviour) item 9).
  - The package holds the value of `frame.image` as one frame that is in CPU memory or in GPU memory. A node that reads the host pixels of a frame in GPU memory copies it one time, and each later reader in the call gets that copy.
- The GPU preprocess of an `onnx_model` node on `cuda`, `trt-rtx` and `directml` ([Behaviour](#behaviour) item 8, `preprocessed_on_cpu`; [ADR-W4NW](../../decisions/entries/W4NW-gpu-preprocess-of-a-model-node-and-its-cpu-warning.md)):
  - The node builds a preprocess session at the first call with a set of frame sizes. The graph has one input for each frame, so a new set needs a new session. The first call with a new set is thus slower by the build time. Each camera of a device has a fixed input of the graph, with the last frame size of that camera. A camera that is not in the call gets a zero frame of that size, so the set of frame sizes changes only when a camera changes its frame size. The `details` of the warning give the reason `graph_refused`, `session_not_built`, `frame_size_cap`, `ep_not_wired` or `quick_check_failed`, and the `cause` text of a refusal.
  - The node builds sessions for at most 4 sets of frame sizes on each device. This limits the GPU memory and the build time when the frame size changes from call to call, for example in the running mode `image`.
  - The graph also gives the output `pixels`, the resize result before the normalization. The run removes this output before it builds the session, because ONNX Runtime computes an output that is not bound.
  - The run makes the IO bindings of the preprocess session and of the model session for each call. The output of the graph stays in GPU memory and goes to the model input with no copy.
  - On `directml`, the graph takes each frame in CPU memory. With ONNX Runtime 1.30.0, a DirectML session that gets its GPU as an EP device does not always read a frame that the caller copied to DML memory before the run. The device id of the bound DML memory is 0 on each GPU, because the session selects the GPU. A binding with an other device id fails at the run.

## Authoring guidance

- A previous-frame input lowers the batch in `video`. A `smooth_keypoints` node after the last `onnx_model` node does not, because it runs on the host, frame by frame, after the batched pass ([ADR-ZYS9](../../decisions/entries/ZYS9-pipeline-outputs-running-sharing-inside-one-run.md) item 5).
- A live caller must give a `timestamp_ms` that increases, for example from the capture clock of the camera.
- Risk: a USB camera can give a cut-off MJPEG frame. When no decoder can read it, `V-pipeline.running-12` refuses the call, and a caller that does not catch `CallRefusedError` stops on that frame. A decoder does not always refuse a cut-off JPEG: nvJPEG can give a full-size frame with wrong pixels and no error, as seen with 4:2:0 frames and 4:2:2 frames. Thus `V-pipeline.running-12` does not catch each damaged frame. The capture side must not give a frame that it knows is damaged ([ADR-P245](decisions/entries/P245-jpeg-frame-input.md)).
- The pipeline file is the same in each running mode. The caller gives a value for each mode, in the config before the start or with `set_params` before the first frame. For example, a caller sets `redetect_interval` of a `redetect_trigger` node to 10 in `live` and to 1 in `video` ([ADR-N5BM](../../decisions/entries/N5BM-set-during-run-and-set-params.md) item 5).
